# TWR–OBML local SQLite source-nonce callback — bounded handoff

Parent: `49c8baad8e2d61b8c188148ae35bbc985a9048e9` (accepted actual OB→Tower source token interop PR #83). Canonical source verifier: `tower/obml_account_namespace_source.py` accepted PR #82. Source producer: `web/ob_tower_account_identity_export.py` accepted PR #80.

`tower/obml_local_source_nonce_ledger.py` implements only the accepted verifier's **caller-injected** `consume_once(account_key, nonce, expires_at_epoch)` callback. It requires an explicit absolute local SQLite file path whose parent exists, stores only a namespaced SHA-256 digest of source account and nonce and expiry, atomically `BEGIN IMMEDIATE`/unique-inserts one claim and denies repeat use after reopening the file. Database errors, malformed inputs, inaccessible ledger and duplicate inserts return a negative result to the canonical source verifier, which fails closed. No raw account, nonce, token or secret is stored in rows. It does not replicate HMAC verification or create another registry/resolver.

Tests use the **real** signed OB token and canonical Tower source verifier; test the same token after a local process-restart simulation, two distinct fresh tokens, competing separate SQLite connections, signing-key error before nonce insertion, expired token, corrupt schema and unsafe path. No production credential is in source or CI.

**Storage limitations that must stay explicit:** This is a local single-host, stable-filesystem adapter, not a proven distributed/multi-node replay ledger, not a production shared-volume authorization, and not guaranteed durable on ephemeral hosted container disks. It has no default path, hosted volume, key configuration, route, daemon, backup, migration/retention service or paid resource. A production Tower deployment must select, secure, audit, back up and test suitable shared durable atomic nonce storage across its actual worker/replica topology. No automatic token cleanup is implemented; expiry already fails in the canonical verifier, while deleting ledger rows without a documented retention/recovery policy risks rollback/replay.

Other draft Tower PR #81 contains a **second full verifier** plus a SQLite ledger for the dedicated Tower branch. Avoid two competing signature authorities; reconcile its genuinely distinct ledger tests with this isolated callback before deciding whether to close or rework that draft. Do not automatically deploy the dedicated Tower branch based on source CI.
