# Grounds GRD199–207 — minimal resident-visible record-access history

The future private Grounds service should not read a resident's personal lease/work context without leaving an internal source record. This code adds a narrow append-only `resident_access_events` ledger to the **fresh source-only SQLite/PostgreSQL baselines**, with required schema/index preflight. It is not a production SIEM, independent Tower authentication, legal retention approval, security review or comprehensive provider access history.

`GroundsWebApp` records **selected successful resident personal GETs before returning their private response**: current resident workspace, My Home, read-only Teller rent projection attempt (including disconnected status), authorized work detail/thread, Move Concierge, and the on-demand access-history view itself. It does NOT collect an IP address, cookies, Tower session material, request body, conversation text, private documents, bank/card data or user agent. Records contain only opaque per-lease/property/unit/subject references, a whitelisted read kind/resource reference, server-generated event ID and timestamp. Failed/denied attempts never reveal personal data through the history endpoint. No client supplies the audit actor, role, resource kind or arbitrary history subject.

Each audit write rechecks a CURRENT original resident TowerScope and current underlying `lease_members` before persistence; failure to persist the audit causes the personal GET to return generic 503 instead of leaking its private payload. The currently authorized resident can request `GET /grounds/api/privacy-history?property_ref=&unit_ref=` and see only their own original lease's last 50 minimal events; another resident with the same unit grant, staff, different property or ended lease gets no history. The view's count is observed before the current history GET is itself appended. Its rendered list is on demand, uses text-only DOM and is erased on context changes.

**Important limitation:** This first-party source ledger covers the selected resident read routes above. It is NOT proof of complete staff access, transport/provider access, underlying database administrator actions or security incident coverage. A real privacy/security operations plan must independently define appropriate retention/deletion, restricted operator audit access, breach response, encryption, monitoring and necessary export, under applicable law and owner approval. Do not use the synthetic tests as a compliance claim. Current code never enables an external logging provider or publishes identity/event records to Clouds or Soulaana.

Unit/HTTP/real disposable PostgreSQL regressions cover source-minimal field projections, independent current active lease check, same-unit other-subject denial, ended lease revocation, successful-read-before-response record, history self-read semantics and no secrets or money in projections. Actual fresh private deployment/migration/backup restore, Tower per-request identity and separate owner-operational release, provider/Teller/Vault certifications, security/accessibility/legal review and explicit owner hosted walkthrough remain mandatory. No paid hosting, live user records or public route are activated.
