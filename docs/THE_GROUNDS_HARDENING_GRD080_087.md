# The Grounds — Privacy and Reliability Hardening (GRD080–087)

**Status:** source-only improvements on [draft Grounds PR #51](https://github.com/LeeTheLilBee/SimpleeMrkTrade/pull/51). This is a fictional/local developer backend, not a deployed resident product. No real tenant records, finance, emergency dispatch, public login, Tower route, or paid Render resource has been activated. The Tower requirements handoff [PR #52](https://github.com/LeeTheLilBee/SimpleeMrkTrade/pull/52) was merged as source-only material, not as an approved live crossing.

## Verified findings and code changes

- **GRD080 — Unit notice audience and read isolation:** Prior `property_notices` targeted a bare `unit_ref`; the same person or a later tenant could have read a notice originally intended for an earlier lease. A unit-targeted notice must now be published against the unit's exact current active `lease_ref`, and cannot be published to a vacant/nonexistent unit. Property-wide announcements remain property-wide. Read state now uses the composite `(notice_ref,lease_ref,subject_ref)` and is distinct for new leases, even where the returning person and unit are the same. An in-app read is *not* legal service, push delivery, or receipt confirmation.
- **GRD081–082 — Appointment scope:** Resident appointment access goes back through the same exact-work/lease authorization as the work request itself. Staff cannot propose an old-lease appointment just because the same resident currently occupies that unit under a new lease. A regression covers old read/history/accept/cancel/propose failures and confirms fresh-lease appointments still work.
- **GRD083 — Defensive intake validation:** Property/unit refs, maintenance categories, descriptions and opaque photo references have explicit upper bounds. Empty, malformed, too-many, NUL-containing and invalid entry-permission values are rejected before persistence. The local application still refuses actual photo upload until its certified Vault adapter exists.
- **GRD084, GRD086 — Local fixture consistency:** Integrity checks report missing critical tables/columns instead of treating an old notice schema as current. Local fixture backups are exclusive-create/no-overwrite, and cleanup cannot delete somebody else's intervening file. `GroundsStore.initialize` refuses a symlink or known obsolete lease-unscoped notice layout rather than silently performing an unsafe partial schema change. This is **not** a real private production database migration or encrypted backup.
- **GRD085, GRD087 — Scheduling and idempotence:** Prospect tours and maintenance appointment windows require timezone-aware future times within 366 days; a maintenance appointment remains capped at eight hours. Previous hardcoded tour test dates are replaced with relative dates to keep the suite useful later. Notice-read idempotence now targets only the exact notice/lease/member unique key instead of broadly ignoring unrelated insert errors.

## Test and release boundaries

The new regressions exercise same-person/same-unit **re-leasing**, old lease unit-specific notices, per-lease property-wide read receipts, old appointment denial, still-authorized current appointment, vacant-unit notice denial, intake boundary values, a legacy local schema, backup overwrite refusal, symlink refusal and invalid scheduling dates. CI continues to compile, test, run the isolated fictional developer walkthrough and validate the visual preview. Check the **latest PR head's** status before calling this completed; earlier passing runs do not validate newer commits.

These schema changes are deliberately for **new, disposable fictional local fixtures**. There is no automatic conversion of prior SQLite files containing personal information. Real tenant data must await an explicit, versioned private-storage migration with backup/restore, legal retention and owner security review.

## Still separate from Grounds domain source

A real Tower resident/staff/owner receiver and exact grant lifecycle; certified signed Vault proofs and file ingestion; Teller payment, refund, pending/returned-payment truth; actual communication provider/receipt/emergency on-call response; housing/accessibility/privacy review; live data hosting and release acceptance are all external launch gates. Soulaana continues read-only and may explain source data, never bypass any of these requirements.
