# Grounds GRD172–180 — protected maintenance timeline and in-app conversations

Grounds now has a source-backed plain-text conversation attached to a **currently authorized** work item. This is not an email, SMS, emergency channel, legal notice, Vault upload, resident consent, or dispatch. Tower still owns the actual per-request current identity/lease/assignment authorization; the production Tower receiver remains externally unimplemented.

- Fresh synthetic SQLite and private-source PostgreSQL baselines include append-only `work_messages` with original author reference/role, property/work scope, shared or staff-only audience, 1–1200 character text and server timestamp. New schema/index are required in fixture and future private PostgreSQL preflight. **The baseline is for a new private deployment only; no existing hosted tenant database or destructive automatic migration is changed.**
- `GroundsWorkThread` delegates to `GroundsOperations._visible_order` inside the same database transaction. Residents may see/post only their own original request tied to their still-active exact lease and unit. A second resident in the same unit does not inherit another person's private messages. Technicians only after exact Tower assignment and currently matching work assignee; they see/post shared messages only. Owner, manager and maintenance supervisor may see shared+internal staff messages and post either. Other roles, other properties, ended leases and closed-work posts fail closed.
- `GET /grounds/api/work-thread?work_ref=` returns only bounded 100-message and 100-state-event projections, count/truncation flags, no author subject IDs, whitelisted timeline, and accurately distinguishes *historical independently verified* delivered event receipts from absent current provider connectivity. It does not include protected Vault evidence, private invoice data, read receipts or a fabricated delivery acknowledgment.
- `POST /grounds/api/work-message` accepts exact fields and a UUIDv4 idempotency key; its message reference is derived by the existing server-owned independent CSRF secret, authenticated session/subject/role, resource and key. Exact retry is recoverable after revalidating current lease/assignment; a changed replay or another author cannot reuse the reference. The insert never mints or sends an external delivery event, and all responses say `external_notification_delivered=false`.
- The actual role-scoped browser adds **Updates & conversation** to authorized maintenance cards. It uses `textContent`, not injected HTML; keeps old-context results hidden under property switching; visibly labels internal staff visibility; and shows a plain-text composer only while source permits posting. The UI never asks for phone numbers, email addresses, photos or legal entry consent. Any future attachments require separately authenticated Tower/Vault routing and receipts.

Source tests cover active-lease original resident vs other member, staff-only redaction, idempotent exact retry vs changed payload, former resident denial, unassigned technician denial, no delivery assertions and WSGI query/role/privacy. Disposable real PostgreSQL integration checks persisted original rows and protected WSGI views. Both exact child and merged parent source and PostgreSQL CI must pass before source acceptance.

External operating concerns remain mandatory: real Tower identity/operational release issuers, private approved DB/restore and retention, moderation/records/privacy policy, human urgent handling, provider recipient resolution/retry and original delivery receipts, accessible owner walkthrough and actual tenants only after signed owner release. This work neither enables real messaging transport nor provides emergency coverage. PR #51 stays draft.
